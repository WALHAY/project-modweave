# ModWeave

## Название проекта
ModWeave - платформа игровых модификаций.

## Краткое описание идеи проекта
Веб-платформа для публикации, хранения и распространения пользовательских модов к играм. Пользователи загружают моды с версиями и файлами, оставляют комментарии, скачивают публичные моды.

## Предметная область и сущности
**Предметная область**: платформы моддинга (Modrinth, CurseForge, NexusMods).  
**Основные сущности**:
- **User** – пользователь платформы
- **Game** – игра (Minecraft, Fallout и др.)
- **Mod** – модификация (принадлежит игре и автору)
- **Version** – версия мода с описанием изменений
- **File** – файл принадлежащий какой-то версии мода
- **Comment** – комментарий к моду
- **Category** – категории модов

## Обоснование актуальности
Моддинг игр растет, но существующие платформы либо закрыты, либо привязаны к играм. Таким образом необходима открытая платформа не привязанная к какой-либо игре.

## Акторы (роли)
1. **Гость** – просмотр модов, скачивание публичных версий
2. **Авторизованный пользователь** – все как гость + публикация модов и комментариев
3. **Админ** – модерация контента; добавление новых категорий, игр

## Пользовательские сценарии

Скачивание мода (гость):
1. гость заходит на главную страницу, выбирает игру из каталога;
2. переходит в раздел модов, применяет фильтры (популярность, дата, категория);
3. открывает страницу мода, читает описание, просматривает версии и комментарии;
4. выбирает последнюю версию, нажимает "скачать";
5. получает ссылку на файл, скачивает его напрямую.

Публикация мода (авторизованный пользователь):
1. пользователь нажимает кнопку "опубликовать мод";
2. переходит на страницу создания модификации; выбирает игру из списка; вводит название мода и первой версии, описание; выбирает категории;
3. нажимает кнопку "опубликовать";
4. мод отправляется на проверку.

Проверка модов (админ):
1. админ заходит в админ-панель;
2. жмет кнопку "модификации на проверке";
3. переходит в карточку очередной модификации;
4. проверяет название, описание, файлы;
5. подтверждает или отклоняет опубликованную модификацию.

## Запуск

Нужны JDK 25 и Docker Compose. Из корня проекта:

```sh
docker compose -f docker/docker-compose.yaml up -d
export JWT_SECRET="$(openssl rand -base64 32)"
```

API доступно на `http://localhost:8080/api/v1`. Секрет JWT обязателен; сохраняйте его между перезапусками, чтобы выпущенные токены продолжали работать. Параметры подключения задаются через `DB_URL`, `DB_USER`, `DB_PASSWORD`, `REDIS_HOST`, `REDIS_PORT`, `S3_ENDPOINT`, `S3_ACCESS_KEY`, `S3_SECRET_KEY` и `S3_REGION`. Значения по умолчанию соответствуют локальному SeaweedFS в Compose. Максимальный размер файла — 100 МБ, multipart-запроса — 500 МБ (`spring.servlet.multipart`).

Локальный SeaweedFS запускается вместе с Compose и использует S3 endpoint `http://localhost:8333`. Учетные данные по умолчанию: `username` / `password`; они задаются в `docker/seaweedfs-s3.json`. Приложение автоматически создает бакеты `mods` и `images`, оставляя бакет файлов приватным и делая изображения общедоступными.

```sh
docker compose -f docker/docker-compose.yaml up -d
./gradlew bootRun
```

Compose создаёт схему и таблицу outbox для очистки хранилища только при первом запуске PostgreSQL с пустым томом. Источники схемы — `sql/init.sql` и `sql/storage-cleanup.sql`; Gradle включает эти файлы в ресурсы. Уникальные индексы требуют отсутствия дубликатов логинов, email, категорий без учёта регистра и путей файлов. Ранее настроенные каталоги данных Docker следует перенести в именованные тома перед переходом на обновлённый Compose.

Регистрация и вход принимают `application/x-www-form-urlencoded`; загрузки — `multipart/form-data`. Примеры находятся в `requests/`. Для обновления отображаемого имени используется поле `name`. Ответы версий содержат UUID версии и файлов; скачивание: `GET /api/v1/files/{fileId}/download`. Гостям доступны одобренные версии, автору и администратору — также версии на проверке и отклонённые. Изменять статус может только администратор. Бакет файлов приватный, изображения публичны.
Администратор просматривает версии, ожидающие проверки, через `GET /api/v1/mods/{modId}/versions?page=0&size=20`: авторизованный владелец мода или администратор видит версии со всеми статусами. Решение принимается через `PATCH /api/v1/mods/{modId}/versions/{versionId}?status=APPROVED` или `REJECTED`.
Спецификация API v2 в формате OpenAPI 3.1 находится в [`docs/openapi.yaml`](docs/openapi.yaml); HTTP-примеры для совместимого API v1 находятся в `requests/`.

Новый пользователь получает обычные права. Для локальной проверки модерации зарегистрируйте пользователя и назначьте ему `is_admin = true` в `modweave.users`, затем перезапустите приложение с очищенным кэшем `users` и войдите заново. `sql/roles.sql` — отдельный пример ролей PostgreSQL; права API проверяет Spring Security.

Тесты репозиториев запускают изолированный PostgreSQL 16 через Testcontainers. При отсутствии Docker можно выполнить проверки сервисов, JWT, HTTP и метаданных Hibernate:

Для отдельной временной PostgreSQL-базы можно заранее применить `sql/init.sql` и `sql/storage-cleanup.sql`, затем задать `MODWEAVE_TEST_DATABASE_URL`, `MODWEAVE_TEST_DATABASE_USER`, `MODWEAVE_TEST_DATABASE_PASSWORD`. Используйте только тестовую базу.

Генератор демонстрационных данных: `python3 -m pip install -r seed/requirements.txt`, затем `python3 seed/main.py`. Он использует `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`; пароль сгенерированных пользователей задаёт `SEED_PASSWORD` (по умолчанию `seed-password`). Пароли сохраняются как BCrypt. Ссылки на файлы в этих данных демонстрационные: генератор не загружает объекты в SeaweedFS.

## WebLab №2 — контракт API

Исходное задание — `labs.pdf`, страницы 5–6; предметная область и сценарии описаны выше. Результат — [OpenAPI 3.1](docs/openapi.yaml), версия 2.0.0. Ветка `web/lab02` содержит проектирование и проверки; реализация v2 относится к следующей лабораторной. Уже существующее API `/api/v1` сохраняется для HTTP-примеров из `requests/`.

Ресурсы: пользователи, игры, категории, моды, версии, файлы, комментарии и коллекции. Отдельный протокол SSE/WebSocket/gRPC не требуется: текущие сценарии состоят из запросов и ответов, файлы передаются по HTTP. Фоновая очистка хранилища — внутренняя задача сервера.

| Сценарий | Шаг | operationId | Успех / ошибка |
|---|---|---|---|
| Скачивание | Открыть каталог игр и модов | `listGames`, `listMods` | 200, страницы; 400 при неверной пагинации |
| Скачивание | Открыть карточку и обсуждение | `getMod`, `listModComments` | 200; 404 для неизвестного мода |
| Скачивание | Получить версии и файл | `listModVersions`, `downloadFile` | 200; гостю доступны только одобренные версии |
| Публикация | Зарегистрироваться и войти | `registerUser`, `login` | 201 и 200; 409 при повторной регистрации, 401 при неверном пароле |
| Публикация | Выбрать игру и категории | `listGames`, `listCategories` | 200 |
| Публикация | Загрузить мод с первой версией | `createMod` | 201, версия PENDING; 400 при неверных данных, 401 без токена, 413 при превышении размера |
| Модерация | Войти администратором, найти мод и версии | `login`, `listMods`, `listModVersions` | 200; администратор видит PENDING и REJECTED |
| Модерация | Принять решение | `moderateVersion` | 200, APPROVED/REJECTED; 403 для обычного пользователя, 400 для PENDING |
| Категории (CRUD) | Создать → прочитать → изменить описание → удалить | `createCategory`, `getCategory`, `updateCategory`, `deleteCategory` | 201 → 200 → 200 → 204; 404 после удаления |

API возвращает `gameId`, категории, дату и счётчики скачиваний. Серверный поиск модов пока поддерживает название; фильтрацию по игре/категории клиент может выполнять по полученным страницам. Это ограничение существующего проекта, а не отдельная реализация фильтров в этой работе. Администратор просматривает версии выбранного мода; отдельной глобальной очереди модерации пока нет.

### Решения по контракту (ADR)

1. **Версионирование и совместимость.** Выбран `/api/v2`, потому что в проекте уже есть v1 и задание №3 требует сохранить оба API. Вместо дублирования домена, сущностей БД и репозиториев новая версия использует существующие слои. Альтернатива — переписать v1 — нарушает совместимость HTTP-примеров.
2. **REST-ресурсы и обновления.** Категория адресуется `/categories/{categoryName}`; её имя неизменно, PATCH меняет только описание, `null` очищает его. Пустой JSON и неизвестные поля запрещены. POST создания возвращает 201 и Location, DELETE категории — 204 без тела. Добавление в коллекцию — POST `/collections/{collectionId}/mods`: операция вставки не идемпотентна, поэтому прежний PUT не переносится в v2. Повторная вставка возвращает 400. Обновление собственного профиля — PATCH `/users/me`.

GET безопасен; учёт скачиваний — побочный статистический эффект. DELETE идемпотентен по конечному состоянию, хотя повторный запрос может вернуть 404. Присваивание описания через PATCH также идемпотентно. Списки используют обязательные `page` от 0 и `size` от 1; размер ограничивается сервером (обычно 100). Категории — небольшой справочник без пагинации. Ответ страницы содержит `page`, `size`, `totalElements`, `totalPages`, `empty`, `content`. Даты сохраняют существующий формат локального времени без часового пояса; он явно описан шаблоном, а не ошибочным RFC 3339 `date-time`. Nullable-поля используют синтаксис OpenAPI 3.1 `type: [string, 'null']`.

JWT выбран для существующего stateless API; access-токен передаётся в `Authorization: Bearer …`, refresh-токен — только в `/auth/refresh`. Роли проверяются сервером. Схема пользователя не раскрывает email, пароль и признак администратора. Ошибки фиксируются кодами 400/401/403/404/409/413/415; формат диагностического тела существующего сервера не является стабильной частью контракта. Отсутствие тела ошибки допустимо. При запросах указаны Content-Type, при загрузке файла — Content-Disposition, при создании адресуемых ресурсов — Location.

### Воспроизводимые проверки без бэкенда

Из корня проекта (Python 3 и Node.js 22.12+):

```sh
python3 -m venv build/openapi-venv
build/openapi-venv/bin/pip install PyYAML==6.0.3 jsonschema==4.26.0 openapi-spec-validator==0.7.2
npx --yes @redocly/cli@2.58.2 lint docs/openapi.yaml --extends minimal
build/openapi-venv/bin/python docs/check_openapi.py
```

Линтер проверяет структуру и правила OpenAPI; скрипт дополнительно проверяет уникальность operationId, префиксы путей, примеры параметров, тел запросов и ответов по JSON Schema 2020-12, включая форматы UUID/email. Версии инструментов зафиксированы в командах, отдельный Node-проект не нужен.

В первом терминале:

```sh
npx --yes @stoplight/prism-cli@5.16.0 mock docs/openapi.yaml --host 127.0.0.1 --port 4010
```

Во втором:

```sh
build/openapi-venv/bin/python docs/check_openapi.py --mock-url http://127.0.0.1:4010
```

Сценарий связывает регистрацию, вход, создание, чтение, PATCH и DELETE категории. Prism возвращает примеры и проверяет контракт: он не хранит изменения и не проверяет реальные роли JWT. Создание категории после обычной регистрации допустимо только в mock; на реальном сервере требуется администратор. Проверки бизнес-логики и реального API относятся к №3. ## WebLab №3 — реализация API

Ветка `web/lab03` создана от `web/lab02` (коммит `a8f7e2a`). API v1 и v2 работают в одном процессе и используют одни сервисы, доменные модели и Repository. JPA-сущности остаются в слое доступа к данным; клиент получает DTO. Создание категории и PATCH её описания принимают JSON с явной проверкой полей, остальные формы и multipart сохранены.

| Область | Реализация |
|---|---|
| Маршрутизация и документация | Spring MVC поддерживает версии 1 и 2; WebConfiguration отдаёт Swagger UI |
| Категории | GET/PATCH/DELETE адресуют имя; POST и PATCH проверяют JSON, описание можно очистить null |
| Профиль, комментарии, коллекции | Создание возвращает 201 и Location; профиль обновляется через `/users/me`, вставка в коллекцию — POST |
| Чтение комментариев | Controller → ICommentService → CommentRepository → JPA, пагинация и устойчивый порядок по дате и UUID |
| Модерация | В v2 только APPROVED/REJECTED; права владельца и администратора проверяют существующие сервисы |
| Остальные операции | Общие существующие обработчики работают для обеих версий |
| TUI/GUI | В исходной ветке отсутствуют. Существующий технологический интерфейс `requests/*.http` продолжает использовать v1 |

Запуск тот же, что в разделе «Запуск». После `./gradlew bootRun` открыть **http://localhost:8080/api/v2/docs**. Swagger UI поставляется локальным WebJar 5.33.1, не требует CDN и читает **http://localhost:8080/api/v2/openapi.yaml** — копию единственного исходного YAML, включённую Gradle в ресурсы сборки.

В Swagger UI раскрыть `login`, нажать **Try it out**, заполнить форму и выполнить запрос. Для защищённых методов скопировать `accessToken` в **Authorize** (без слова Bearer). Администратор нужен для категорий, игр и модерации; назначение локального администратора описано выше. Загрузки используют файловые поля multipart. Можно одновременно выполнять запросы обеих версий:

```sh
curl http://localhost:8080/api/v1/categories
curl http://localhost:8080/api/v2/categories
```

Контрактные тесты используют HTTP на случайном локальном порту и изолированные контейнеры PostgreSQL/SeaweedFS, без подмены сервисов и репозиториев. Redis отключён только в тестовом контексте. Проверяются все 36 operationId, статусы, JSON Schema 2020-12, обязательные поля и заголовки, сохранение изменения, очистка nullable-поля, неверные данные, отсутствие ресурса, 401/403, полный путь от публикации до модерации и скачивания, комментарии, коллекции, совместимость v1 и ресурсы Swagger UI.

```sh
./gradlew test --tests 'git.walhay.modweave.integration.ApiContractTest'
./gradlew test ktfmtCheck bootJar
```

Отчёт: `build/reports/tests/test/index.html`. В `ApiContractTest` также проверяется, что удаление обязательного поля из полученного ответа обнаруживается валидатором. Дополнительно проведён эксперимент с реализацией: временная замена 201 на 200 в `CategoryController.createCategory` приводит к падению теста `category CRUD…`; после восстановления правильного ответа тест проходит. Для повторения достаточно изменить этот статус, выполнить первый тест командой ниже, затем вернуть 201 и повторить полный прогон:

```sh
./gradlew test --tests 'git.walhay.modweave.integration.ApiContractTest.category CRUD*'
```

При проверке уточнены две детали спецификации: сериализованное поле страницы называется `empty`, а существующий валидатор изображений поддерживает PNG/JPEG. Исправлены два обнаруженных интеграционным сценарием дефекта JPA: категории мода должны быть изменяемым набором для Hibernate merge; при удалении версии необходимо убрать ссылку из загруженной коллекции родительского мода. Это не меняет схему БД и сохраняет поведение v1.
