# Ревью работы с ИИ

## WebLab №3

Задача: завершить реализацию [лабораторной №3](labs.pdf), проверить соответствие [OpenAPI](openapi/openapi.yaml), добавить простой Spring HATEOAS после чтения его документации. Инструмент: Codex (GPT-6), навык `ecc:documentation-lookup`; официальный справочник прочитан напрямую, поскольку Context7 в сессии недоступен.

План: сопоставить операции с контроллерами/DTO, проверить границы домена и Repository, сохранить v1, выполнить сквозной CRUD категории и остальные пользовательские сценарии на настоящем HTTP-сервере с PostgreSQL/S3. Существующие сценарии публикации, модерации и скачивания сохранены. Новый TUI не создаётся: исходников прежнего TUI/GUI в текущем проекте нет.

Ревью выявило самописное раскрытие ссылок и отсутствие обязательных файлов контекста/ревью. Принято использовать `Link` из Spring HATEOAS и добавить эти материалы. Переход на HAL отклонён: он меняет действующий JSON-контракт без необходимости. Обоснование и альтернативы — [ADR-001/002](docs/architecture/decisions.md).

После изменения выполнен полный цикл: компиляция, линтер, тесты, ревью импортов и diff. На 22.10.2026 `check ktfmtCheck bootJar` проходит: 69 тестов, без ошибок и пропусков; все 37 operationId проверены на реальном сервере. Arazzo: 6 шагов и 24 проверки. Временный статус 200 вместо 201 в `CategoryController` вызвал ожидаемое падение `validation.response.status.unknown`; код восстановлен, повторный полный прогон успешен. Затем убрано ручное кодирование query-ссылок в пользу `Link.expand`, и полный прогон повторён. В Chromium через Swagger выполнены регистрация, вход, Authorize и CRUD категории с PATCH/null. YAML в UI и JAR совпадает с собранным контрактом.

Реализация и матрица требований: [docs/lab-review.md](docs/lab-review.md), раздел «Проверка 22.10.2026». Команды запуска: [README](README.md). Генерируемые логи и JUnit-отчёты находятся в `build`. Исходный OpenAPI и ожидаемые результаты тестов сохранены: формат ссылок не изменился.

## Упрощение HATEOAS по уточнению пользователя

Задача: уменьшить объём собственного кода и переиспользовать Spring HATEOAS. Принято: `WebMvcLinkBuilder.linkTo(Method, ...)`, `RepresentationModelAssembler` и адаптер над `EntityModel`. Из семи файлов DTO удалены `withLinks` и карты ссылок, строки маршрутов и HTTP-методов заменены ссылками на контроллеры. Location и файловый Link строятся той же функцией. Общий advice сохранён для совместимости v1/v2 и кэширования: дублировать контроллеры ради разных представлений не требуется.

`methodOn` проверен на текущих зависимостях и отклонён из-за невозможности проксировать финальный Kotlin DTO; использован документированный вариант с Method. Новый тест проверяет context path, кодирование кириллицы и `+` в пути/query, HTTP-метод и отсутствие нераскрытых шаблонов. Существующие HTTP-тесты всех 37 операций проходят с новым assembler без смены OpenAPI и ожидаемых ответов. При полном прогоне выявлен отсутствующий импорт assembler в ограниченном `@WebMvcTest`-контексте; конфигурация теста исправлена, затем проверки повторены.

Результат повторной проверки: 70 тестов без ошибок/пропусков, `check ktfmtCheck bootJar` успешны. Swagger на новом JAR проверен через Try it out / Execute: регистрация, вход, Authorize и полный CRUD категории, включая PATCH/null. Логи — `build/hateoas-assembler-verification.log` и `build/hateoas-assembler-swagger-check.log`. Объём DTO и кода гипермедиа уменьшился с 475 до 453 строк; схема OpenAPI сохранена.

## Замена MinIO SDK для SeaweedFS

По запросу пользователя прочитаны официальные Java-клиенты SeaweedFS и AWS SDK. Выбран AWS S3Client 2.57.2: существующий сервер используется через S3; нативный seaweedfs-client 4.38 работает через Filer/gRPC и не предоставляет S3-политики, а его опубликованный код недостаточно строго передаёт некоторые ошибки. Решение объяснено пользователю и в ADR-004. Удалены зависимости MinIO из приложения и тестов, S3-операции переведены на стандартный SDK с одним JDK HTTP-клиентом.

На первом интеграционном прогоне обнаружены NoSuchBucketPolicy при удалении отсутствующей политики и несовместимость optional checksum-трейлеров SeaweedFS 4.48. Обработан только ожидаемый NoSuchBucketPolicy; включены path-style, обычный PUT и WHEN_REQUIRED. Потоки открываются заново для retry и закрываются при успехе/сбое. Тест с потоком без mark/reset проверяет полную повторную передачу 256 КБ и закрытие обоих потоков.

Полный check/ktfmtCheck/bootJar успешен: 72 теста без ошибок и пропусков, включая 10 проверок компенсации БД/S3 и все 37 операций OpenAPI. На реальном SeaweedFS проверены передача 256 КБ с Unicode/пробелом/+ в ключе, приватность файлов, публичность картинок и повторный DELETE. Лог — build/seaweedfs-sdk-full-verification.log. В JAR есть AWS S3 SDK, отсутствуют MinIO и лишние Apache/Netty HTTP-клиенты; YAML совпадает с собранным контрактом. Известные недостатки imagePath, публичной видимости обложек и определения MIME остаются отдельной задачей; эта замена транспорта их не исправляет.

## Исправление картинок модов и игр

По запросу пользователя закрыта публичная политика картинок, включая существующий бакет. Добавлен один ImageController для обложек модов/игр, DTO возвращают готовый URL API и _links.image. Видимость обложки следует карточке до 304 и S3. PNG/JPEG определяются по содержимому; расширение проверяется, максимум 4096 пикселей по стороне / 16 мегапикселей проверяется до декодирования. Старые S3-объекты с неправильным MIME исправляются при выдаче. Схема БД, ключи и компенсация/outbox сохранены; v1 получает рабочий imagePath v2. Решение — ADR-005.

Полный check/ktfmtCheck/bootJar успешен: 75 тестов, без ошибок и пропусков, контрактные проверки всех 39 operationId. Проверены guest/owner/admin для PENDING, approval/revocation/delete, GET/HEAD/304, PNG/JPEG, неверный MIME, missing image, ограничения декодирования, закрытие потока и отсутствие S3-чтения при 304. Новый тест сначала не компилировался из-за nullable ETag в mock-заголовке; исправлен requireNotNull, затем полный прогон успешен. Лог — build/image-fix-final-verification.log.

На изолированных PostgreSQL/SeaweedFS и новом JAR проверены imagePath, запрет прямого S3 (403), гостевые 404 и owner 200/304 для PENDING, гостевой 200 после approval. В Chromium оба img.src из API отображаются; Swagger показывает 39 операций, YAML совпадает с собранным. Логи — build/image-fix-http-results.log и build/image-fix-browser-results.log. Временное окружение удалено, штатные Compose-сервисы сохранены.

## Изоляция доменной пагинации от Spring Data

По запросу пользователя удалены Pageable, Spring PageRequest и Sort из доменных сервисов и шести интерфейсов Repository, а также зависимость domain от spring-data-commons. Добавлены собственные PageRequest, SortOrder и SortDirection. API преобразует стандартную HTTP-сортировку после проверки полей и добавления уникального поля; persistence преобразует доменный запрос в Spring Pageable. Ограничение размера страницы остаётся в домене. Решение — ADR-006; README и AI_CONTEXT актуализированы.

Добавлены проверки передачи повторяемого sort из HTTP в доменный запрос и выполнения пагинации с несколькими направлениями сортировки в PostgreSQL. Проверяются порядок полей, ignoreCase, смещение и метаданные страницы; существующая проверка ограничения размера дополнена сохранением номера и сортировки. При компиляции выявлено, что Sort.map возвращает Streamable; преобразование исправлено через toList().map.

Полный check/ktfmtCheck/bootJar успешен: 77 тестов, без ошибок и пропусков. OpenAPI и поведение v1/v2 сохранены. Gradle dependencyInsight подтверждает отсутствие spring-data в compileClasspath домена. Лог — build/pagination-verification.log.
