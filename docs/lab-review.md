# Проверка WebLab №2 и №3

Основание: [labs.pdf](../labs.pdf), страницы 5–8, и [OpenAPI 3.1, версия 2.1.2](../openapi/openapi.yaml). Рабочая ветка — `web/lab03`. Обязательные требования и ИИ-трек проверяются отдельно от необязательных бонусов. Использованы Codex и навыки `ecc:api-design`, `ecc:springboot-security`, `ecc:springboot-verification`.

| Сценарий | Шаг | operationId |
|---|---|---|
| Скачивание | Каталог игр и модов | `listGames`, `listMods` |
| Скачивание | Карточка и обсуждение | `getMod`, `listModComments` |
| Скачивание | Одобренная версия и файл | `listModVersions`, `getModVersion`, `downloadFile` |
| Публикация | Регистрация и вход | `registerUser`, `login` |
| Публикация | Выбор игры и категорий | `listGames`, `listCategories` |
| Публикация | Мод с первой PENDING-версией | `createMod` |
| Публикация | Собственные публикации и новые версии | `listUserMods`, `createVersion` |
| Модерация | Вход администратором и каталог | `login`, `listMods` |
| Модерация | Версии и файлы до публикации | `listModVersions`, `getModVersion`, `downloadFile` |
| Модерация | APPROVED/REJECTED | `moderateVersion` |
| Справочник | Полный CRUD категории | `createCategory`, `getCategory`, `updateCategory`, `deleteCategory` |

Серверный поиск модов ограничен названием; отдельной фильтрации по игре/категории и глобальной очереди модерации нет. Клиент выбирает по полям `gameId`/`categories` полученных страниц, администратор обходит версии из каталога. Поля сортировки ограничены контрактом, порядок стабилизирован уникальным идентификатором.

## Решения и содержательные уточнения

- Ресурсы — пользователи, игры, категории, моды, версии, файлы, комментарии и коллекции. Файл доступен непосредственно по своему URI; GET используется для чтения. Счётчик скачиваний — статистический побочный эффект, 304 его не меняет.
- POST создаёт адресуемый ресурс с 201 и Location; DELETE v2 возвращает 204 без тела. Добавление элемента коллекции — POST с JSON: повторная вставка возвращает 400. DELETE идемпотентен по конечному состоянию, повторное удаление может вернуть 404.
- PATCH категории принимает только `description`; null очищает его. PATCH версии принимает только APPROVED/REJECTED. JSON связывается с Kotlin DTO официальным модулем Jackson; обязательность полей, null и ограничения проверяют Jackson и Bean Validation. Лишние поля и преобразование чисел/boolean в строки отклоняются. Присваивание одного значения PATCH идемпотентно.
- HATEOAS использует совместимую с контрактом JSON-форму `_links: {relation: {href, method}}`, сохраняя `content`/`items`. DTO описывают связи через `ApiResource`, `PageResponseDto` добавляет навигацию страниц. Общий advice подключает ссылки и HTTP-кэширование без изменения JSON-дерева и списка условий для всех типов DTO. Все URI кодируются; ссылки списков включают обязательную пагинацию.
- По уточнённому требованию пользователя мод до первого одобрения скрыт от всех, кроме автора/администратора. Исправлен обход фильтра в `JpaModRepository`. Обсуждение скрытого мода также недоступно. Правила отражены в YAML и HTTP-тестах.
- HTTP-кэш требует перепроверки (`private, no-cache`, `Vary: Authorization`); разрешения проверяются до 304. ETag формируется по представлению, включая доступные ссылки. `Last-Modified` возвращают только файлы, на основании даты загрузки версии. JSON использует ETag без искусственных дат и кэша валидаторов в процессе. Разбор и сравнение `If-None-Match` выполняет Spring `ETag`, включая слабые теги, списки и `*`.
- JWT обрабатывает стандартный Resource Server, самописный фильтр и JJWT удалены. Подпись HS256 использует внешний секрет; refresh не принимается как access. Права аккаунта перечитываются через сервис, без кэша публичного профиля. Разделение типов токена и проверки ролей сохраняют интерфейс v1/v2.
- Слои находятся в `layers/domain`, `layers/persistence`, `layers/api` вместо прежних `layers/business-logic`, `layers/data-access`, `layers/ui`. Пакетный префикс не дублируется каталогами. Убраны неиспользуемые обёртки сортировки/пагинации, мёртвые исключения и дубли зависимостей Gradle.
- Повторная проверка стандартным валидатором выявила два пробела контракта: повторяемый `sort` был описан строкой, а ошибки с JSON-телом — ответами без тела. В версии 2.1.2 `sort` описан массивом с `style: form, explode: true`; ошибки — схемой RFC 9457 `Problem`. Сервер возвращает её через `ResponseEntityExceptionHandler` и общий обработчик доменных ошибок. Пять одинаковых обработчиков по ресурсам удалены. Обработчик bearer-ошибок делегирует статус и `WWW-Authenticate` Spring Security, затем добавляет `ProblemDetail`.
- `Cache-Control`, `ETag`, а для файлов также `Last-Modified` и `Link`, помечены обязательными в соответствующих ответах. Эти заголовки уже возвращались сервером; контракт теперь проверяет их наличие явно.
- Найденные тестами дефекты: повреждённое PNG вызывало 500, теперь возвращает 400; PATCH с неверным Content-Type возвращает 415; проверка видимости комментария больше не приводит к откату вложенной транзакции с ошибкой 500. Условные запросы проверяют доступ перед возвратом 304.

## Воспроизведение и результаты

Команды находятся в [README](../README.md#проверки-лабораторных-2-и-3). Отчёт тестов — `build/reports/tests/test/index.html`. Mock не хранит изменения и не подтверждает права; это проверяют HTTP-тесты с отдельными контейнерами.

Контрактные проверки используют `openapi-request-validator-core:3.0.0` с поддержкой OpenAPI 3.1. Проверяются ответы всех запросов v2, включая ошибки и переходы по ссылкам; для успешных запросов также проверяются путь, параметры и JSON/urlencoded-тело. Валидатор не проверяет схему multipart-тела: такие загрузки проверяются отдельными HTTP-сценариями на реальном сервере и тестами сервисов. Бинарный ответ проверяется сравнением байтов.

В адаптере `OpenApiContract` учтены особенности библиотеки: отключена автоматическая подстановка отсутствующего `additionalProperties: false`, а схема массива query-параметра адаптируется к ожидаемому Java-классу без потери её свойств. Проверки чувствительности подтверждают обязательные поля, nullable-типы 3.1, явно запрещённые дополнительные поля, статус, Content-Type, Location, заголовки кэша и ограничения query-параметров.

Для ручного эксперимента чувствительности временно заменить `ResponseEntity.created(location).body(result)` на `ResponseEntity.ok(result)` в `CategoryController.createCategory`, выполнить `./gradlew test --tests 'git.walhay.modweave.integration.ApiContractTest.category CRUD*'`, убедиться в ошибке `validation.response.status.unknown` для 200, восстановить код и повторить проверку.


Проверка 11.10.2026:

- `./gradlew check ktfmtCheck bootJar testOpenApi` (при запущенном mock): 69 тестов, 0 ошибок и пропусков; JAR собирается. Семь HTTP-сценариев проверяют все 37 операций. Лимит multipart в тестовом контексте уменьшен до 1 КБ для воспроизводимой проверки 413; рабочие ограничения 100/500 МБ сохранены.
- После упрощения повторён полный прогон: проверены строгие JSON-типы, PATCH/null, отсутствие искусственного Last-Modified, переходы по ссылкам с кириллицей, пробелами и `+`, включая фильтры и страницы. JAR содержит Kotlin-модуль Jackson и актуальный собранный контракт.
- Redocly: OpenAPI и Arazzo валидны, примеры проходят проверку схем. Prism + `testOpenApi`: 1 workflow, 6 шагов и 24 проверки проходят.
- Chromium/Playwright: Swagger показывает 37 операций. Через Try it out / Execute выполнены GET категорий (200), регистрация (201 + Location), вход (200), Authorize и создание категории администратором (201 + HATEOAS). Ошибок JavaScript нет; отданный YAML побайтно совпадает с собранным исходником.
- Эксперимент с реализацией: временный статус 200 у `createCategory` вызвал ожидаемое падение `validation.response.status.unknown`; контроллер восстановлен, затем повторён полный успешный прогон. Лог — `build/mutation-check.log`, сообщение валидатора — `build/mutation-result.txt`.
- Проверены зависимости модулей, соответствие новых пакетов каталогам, отсутствие потерянных файлов при переносе, ссылок из контроллеров на JPA и оставшихся ссылок на JJWT/самописный JWT-фильтр.

Статические проверки: компиляция Kotlin, `ktfmtCheck`, линтер OpenAPI и проверка направлений импортов между слоями. Detekt/SpotBugs, JaCoCo и отдельный CVE-сканер в проекте не настроены; процент покрытия и отсутствие уязвимостей зависимостей этим прогоном не утверждаются.

Логи локального прогона: `build/final-verification.log` (включая mock-сценарий), `build/swagger-check.log`; снимок Swagger — `build/swagger-verified.png`. Это генерируемые артефакты; команды выше воспроизводят проверки на другом компьютере. Устную защиту и знание HTTP автоматические тесты не заменяют.
